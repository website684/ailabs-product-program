Browser Use + Governed Sourcing Data Store

Give AI Labs agents a browser, so they can work on the large part of the web that has no API — and a governed place to put what they find. First use case: candidate sourcing for the Recruiter Agent.

1Why this matters now

Our agents can only act where an API exists. Today an AI Labs agent reaches the world through the tool registry (HTTP tools) and MCP servers. That covers our own systems and modern SaaS — and almost nothing else. The surfaces where frontline recruiting actually happens are browser-only:

  • apna, WorkIndia, JobStreet, FastJobs — the boards where India/SEA frontline candidates live — expose no candidate-search API to employers. WorkIndia alone connects ~30M jobseekers to ~100K businesses a month.
  • Every incumbent AI sourcer (LinkedIn Hiring Assistant, Juicebox, hireEZ, SeekOut) targets white-collar, API-indexed talent. None of them can reach frontline boards — by design. This is open whitespace, not a feature race.
  • The same constraint blocks other roadmap items: competitor price checks, vendor portal tasks, government-portal filings — all browser-only.
Browser use turns "there's no API" from a roadmap blocker into a configuration task. It runs on the same guardrail, audit and credit machinery every other step type already gets.
We already sell it. The AI Labs sales deck (betterplace.co.in/studio → ai-labs, slide 1) promises agents that "make real phone calls in 24 languages, read documents, analyse photos and video, browse the web, and do real work inside your systems." The public site's roster ships "hooks", voice, and documents — but no agent can browse anything today. This PRD closes a gap between the promise our sales narrative already makes and what the platform delivers.

Why now: 2026-era browser-agent stacks have converged on hybrid perception (accessibility-tree first, vision fallback) that is reliable and cheap enough for production pilots — this wasn't true 18 months ago. And our platform already has the primitives a safe rollout needs: typed steps, HITL escalation (WAITING_FOR_HUMAN), session recording, guardrail events, credit metering.

2Goals & non-goals

Goals (v1)
  • New BROWSER step type usable in WORKFLOW_AGENT DAGs and as an agent tool
  • Scoped, recorded, HITL-gated browser sessions on an org-approved site allowlist
  • Structured extraction into a governed Datasets store with provenance + consent lifecycle
  • Recruiter Agent sourcing on JobStreet/FastJobs/apna-class boards as the pilot
Non-goals (v1)
  • No LinkedIn (hard ToS prohibition — see red lines)
  • No login-gated actions, purchases, form submissions, or messaging on external sites
  • No autonomous outreach to sourced candidates (HITL always)
  • No general "agent surfs the open web" — allowlisted sites only
  • No CAPTCHA bypass — CAPTCHAs hand off to a human

3How it works

3.1 Execution flow

Agent plans task→ HITL scope approval→ Browser Runtime session→ act / extract loop→ structured records → Datasets→ recording + log → run audit

A BROWSER step declares: target sites (must be on the org allowlist), allowed action classes (read / search / extract vs interact), an extraction schema, and budgets (time, pages, credits). Before execution, the run pauses at a scope-approval gate — the requester sees exactly what will and won't be done (the demo shows this card verbatim). Approval is logged as a guardrail event; denial parks the step.

3.2 Browser Runtime Service (new microservice)

  • Pool of headless Chromium workers (Playwright/CDP) in isolated pods; one org never shares a browser profile with another. Fits the existing service estate + k8s patterns.
  • Perception: accessibility-tree/DOM first, vision fallback only for canvas-heavy or verification moments — cheaper and more reliable on job-board list views than screenshot loops. Tradeoff accepted: per-site brittleness to DOM changes → per-site selector packs maintained like connector configs.
  • Action loop driven by an LLM step with a constrained action space (navigate, search, read, extract, paginate, wait). Every action is journaled with timestamp + URL.
  • Session recording (video + action log) stored to S3 via the existing session-media path and linked from RunInspector for replay. The recording is the audit trail, so it cannot be optional.
  • Identity: vaulted per-org service accounts where a site requires auth (v2) — never a recruiter's personal login. v1 is logged-out public pages only.
  • Anti-bot posture: honest rate-limiting, human-like pacing, robots/ToS-reviewed sites only. Assume Cloudflare-class defenses exist; when blocked or CAPTCHA'd → WAITING_FOR_HUMAN, never bypass.
  • Events stream over RTS so the requester can watch the session live (as in the demo) and kill it at any time.

3.3 Human-in-the-loop model

Risk-tiered gates enforced by the execution wrapper outside the model (OWASP Agentic-Top-10 aligned): Tier 0 read/extract on allowlisted sites — approve once per session. Tier 1 any new site, any interaction beyond read — explicit approval each time. Tier 2 anything irreversible (sending, submitting, paying) — not available in v1 at all. Every approval/denial/timeout is a logged guardrail event.

4The governed data store — Datasets

Browser sourcing is only as valuable as what we keep. Ad-hoc scrape output (spreadsheets, JSON blobs) fails three ways: no provenance, no dedupe, no lawful lifecycle. Datasets is a new platform primitive: org-scoped, schema'd collections that agents read and write through tools — the first collection is candidate_pool.

candidate_pool record (v1)
{ candidate_id, org_id, fields{ name, phone_hash, area, experience[], availability… },
  provenance{ source_url, source_site, fetched_at, run_id, extraction_confidence, match_rationale, jurisdiction },
  consent{ state, basis, policy_version, timestamps[], opt_out_honored_at },
  lifecycle{ retention_due, purge_job_id }, dedupe{ identity_key: phone/email hash, merged_from[] } }

Consent lifecycle (the part that makes cold sourcing lawful)

SOURCED_NO_CONSENT→ OUTREACH_SENT (opt-in ask)→ CONSENTED / DECLINED → purge / EXPIRED → purge→ ACTIVE_CANDIDATE
  • Pre-consent, the only permitted contact is the single opt-in ask (with source disclosure + one-tap STOP). STOP triggers immediate purge — demoed verbatim in the outreach preview.
  • Retention: sourced-but-never-consented records auto-purge at a configured window (default 90 days). Fixes the "indefinite future-opportunities" pattern regulators flag.
  • Dedupe: identity-key merge (phone/email hash, Beamery pattern); provenance is immutable — if a sourced candidate later applies directly, both sources are kept.
  • Re-enrichment: scheduled refresh for externally-sourced fields (Gem pattern), not one-shot scrapes.

5Compliance & red lines

Hard red lines (non-negotiable in any phase):
  • No LinkedIn scraping — live ToS §8.2 prohibition, enforceable via contract independent of CFAA (hiQ aftermath).
  • "Publicly available" is not a cross-border green light: India DPDPA's exemption is narrow (self-posted data, no cross-enrichment); Indonesia has none.
  • No new source site without a logged per-site ToS review in the registry.
  • No personal credentials — vaulted service accounts only (v2+).
  • No indefinite retention of non-applicant data — purge job is a launch blocker, not a fast-follow.
JurisdictionLawful basis for sourced data (v1 posture)
India (DPDPA)§3(2)(b) publicly-available exemption — narrow: self-posted job-board data only, no enrichment across sources pre-consent
Singapore (PDPA)Deemed consent for job-portal-posted data — but time-bound retention and no multi-employer forwarding without fresh consent
Malaysia (PDPA '24)Opt-in ask on first touch; biometric/sensitive fields never sourced
Indonesia (UU PDP)No public-data exemption — consent-first market: pool + inbound only until legal review clears sourcing

7Success metrics

  • Task success: ≥ 65% of browser-sourcing sessions complete without human rescue (plan for 60–75% real-world, not the 89–94% seen on academic benchmarks) — remainder hand off gracefully.
  • Sourcing yield: ≥ 10 qualified profiles per session-hour on pilot boards; cost/profile tracked per site.
  • Recruiter outcomes (pilot pod): time-to-first-contact in minutes (vs >60% drop-off baseline); WhatsApp response ≥ 60% (vs ~30% call baseline); directional cost-per-hire −70% with pool-first + sourcing + screening combined.
  • Compliance (hard gates): 100% of sourced records carry a full provenance tuple · 100% of outreach passes a logged HITL gate · 0 irreversible auto-actions · purge SLA met 100%.

9Risks & open questions

  • ToS/legal drift — boards can change terms; mitigation: per-site review log + kill switch per site. Owner: legal.
  • Anti-bot arms race — success rates may degrade; mitigation: honest pacing, partnerships where possible (some boards may prefer a data deal once we show volume). Open: pursue official partnerships with JobStreet/apna in parallel?
  • Selector brittleness — DOM changes break extraction; mitigation: confidence scores per field + nightly canary tasks per site.
  • Cost creep — idle waits burn session-hours; mitigation: batch lookups per session, hard budgets per step.
  • Open: does Datasets live in ghost_operators or as its own service? (Recommend: repo layer in ghost_operators for P1, split at P2 if a second collection type lands.)
  • Open: Indonesia launch posture pending legal review (no public-data exemption).
