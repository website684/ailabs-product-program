Seven capabilities I want on the roadmap

ONE-PAGER · 01

Artifact generation — agents that hand you a finished document

Our agents can read documents and talk about them. I want them to hand you one back.

Why I want this

Look at what our customers actually do after talking to an agent today: they take the answer and go make a document out of it somewhere else. Offer letters, payroll summaries, shift rosters, training certificates, JD posts, weekly MIS. That last step is ours to take. An AI employee that ends every task with "here's the file" feels finished. One that ends with a paragraph of text feels like a chatbot.

This also compounds everything else on this list — artifacts are what you send over Gmail, drop into Drive, and deliver on WhatsApp.

How it works on our platform

  • A new step capability: generate artifact — LLM step output flows into an org-branded template (DOCX/PDF/XLSX to start), renders server-side, lands in S3.
  • Delivery through what we already have: the download widget in chat, a WhatsApp document message, or a WRITE step into the org's systems.
  • Templates live at org level like tools do — create once, any agent uses them. Marketplace templates ship with their own (Mia ships an offer-letter and crew-ID template out of the box).
  • Every artifact carries provenance: which run, which step, which data. If we generate a payslip summary, I want to trace every number in it.
HAVE: download widgetHAVE: S3 + session mediaHAVE: run provenanceBUILD: template rendererBUILD: artifact step config
Ship first: offer letter + completion certificate for Mia, payroll summary sheet for the payroll agents. Measure: % of runs that end in a downloaded/delivered file. If nobody downloads, we built the wrong templates.
ONE-PAGER · 02

Gmail, Slack, Drive connectors — meet work where it already lives

Every enterprise we sell to runs on Google Workspace and Slack. Our agents should treat those as home turf, not integrations.

Why I want this

Right now, when Mia finishes onboarding someone, a human copies the result into an email. When a check fails, a human tells the ops channel. That's us doing 95% of the work and leaving the visible 5% to manual effort — so the customer remembers the manual part. The connectors are small builds with outsized perceived value: they're where the agent's work becomes visible to the rest of the company.

How it works on our platform

  • Ship all three as first-party MCP servers in the MCP Registry — same rails as everything else, nothing bespoke. Gmail: send/draft with org templates. Slack: post to channel, DM summaries, escalation pings. Drive: read a folder into the Knowledge Base (with resync), write artifacts back.
  • Org admin connects once with a scoped service account — never a personal login. Agents get the capability through the normal tool picker; steps get it through step-level attachment.
  • These become platform-ready capabilities in the marketplace install wizard — the "Ready ✓ · platform" row. Install Mia, tick Gmail, offer letters go out on their own.
  • Drive-to-KB sync quietly fixes our biggest KB complaint: stale documents. The org's policy folder IS the knowledge base.
HAVE: MCP registry + attachmentHAVE: encrypted secrets, WRITE outboxHAVE: KB ingestion pipelineBUILD: 3 connector servers + OAuth admin flow
Ship first: Slack escalations (smallest, most visible — every WAITING_FOR_HUMAN pings the ops channel), then Drive→KB sync, then Gmail send. Measure: % of installs that connect at least one; time from exception to human response.
ONE-PAGER · 03

Thumbs up / thumbs down — the cheapest trust signal we're not collecting

We already built the feedback backend. There's just no thumb to press.

Why I want this

My number one roadmap bet is the trust layer — an enterprise hires AI employees when it can review them like human ones. Reviews need signal, and the cheapest, highest-volume signal in the industry is a thumb on every response. We have a feedback module with seven endpoints sitting in ghost_operators and almost nothing feeding it. That's a finished kitchen with no waiters.

One rule, though: a thumbs-down must go somewhere. Feedback that disappears into a table trains users to stop giving it.

How it works on our platform

  • 👍👎 on every agent response in the chat UI (agent-ui renderer, embed included), with an optional one-tap reason on thumbs-down: wrong answer / didn't understand / too slow / other.
  • Signals land against the run + step (the feedback module already models this), so a bad rating points at the exact step and prompt that produced it.
  • Surface it in three places: the Analytics quality tab (rating per agent, trending), the Run inspector (rated turns flagged inline), and the marketplace listing (outcome + satisfaction, not star vanity).
  • Close the loop: thumbs-down clusters become the eval set for the next prompt/template version. This is how templates get better between versions without guessing.
HAVE: feedback module (7 endpoints)HAVE: analytics quality tabHAVE: run/step tracingBUILD: chat widget + aggregation views
Ship first: the thumb in agent-ui + a rating column in analytics. Two weeks of work, mostly frontend. Measure: feedback rate per 100 responses (target 5%+), and whether thumbs-down rate drops release over release — that's the trust layer becoming real.
ONE-PAGER · 04

New widgets — the vocabulary of our conversations

Widgets are why our agents feel like products instead of chatbots. Sixteen types got us here; the roster needs about six more.

Why I want this

Every good moment in our demos is a widget: the job card, the camera capture, the MCQ. Text is what agents fall back to when we haven't built the right widget yet. I look at the roster and the templates we want to sell, and the gaps are obvious — each missing widget is a template we can't ship or a flow that degrades into typing.

What to build, in order

  • reel_player — Skilling reels with the MCQ frame, inside chat. Makes Theo real and completes the training step of every onboarding template. Biggest single win, and the LMS content already exists.
  • signature — draw-to-sign for offer acceptance and consent. Pairs with artifact generation (sign the generated letter without leaving chat).
  • calendar_slots — pick an interview/visit slot. Jack books interviews today through prose; that's silly.
  • payment_upi — collect a fee or deposit in-flow (gig onboarding, training fees). Needs the payments team, so start the conversation now.
  • data_table — structured rows with sort/confirm, for payroll normalizers and MIS agents that currently dump JSON into text.
  • voice_note — record-and-send for candidates who won't type. This is India frontline; voice is not a nice-to-have.

Standard applies to all six: registered in widget_registry with a schema, dataTemplate + outputKeyMap like every existing widget, graceful text fallback, works in embed. Nothing ships as a one-off renderer.

HAVE: widget_registry + 16 typesHAVE: builder mapping UXHAVE: reels + MCQ content (Skilling)BUILD: 6 renderers + schemas
Ship first: reel_player — it's already on the capability-map build list and blocks the Mia template. Measure per widget: usage per 100 runs and step-completion rate vs the text fallback. A widget that doesn't beat text gets cut.
ONE-PAGER · 05

WhatsApp integration — the channel our users already open 40 times a day

For frontline India and SEA, WhatsApp isn't a channel. It's THE channel. Everything else is where we make them come to us.

Why I want this

The research keeps saying the same thing: 60–80% response rates on WhatsApp against ~30% for calls, 85% completion for chat-delivered training against 20–30% for LMS logins, and the biggest drop-offs in every funnel are exactly where we force a candidate to switch surfaces. We built beautiful chat experiences and then asked users to find them. WhatsApp inverts that — the agent shows up where the person already is. This is the single highest-leverage distribution decision on the roadmap.

How it works on our platform

  • BSP integration (Meta Cloud API or a partner — decide on rate cards) living beside Plivo in channel_open. One more edge; ghost_operators doesn't change.
  • Sessions key to the phone number — a candidate can drop off Tuesday and resume Thursday with context intact. This is principle #4 from the onboarding research; WhatsApp makes it native.
  • Widgets degrade gracefully: quick replies → WhatsApp buttons, cards → media messages, forms → guided Q&A, artifacts → document messages. The widget schema already separates content from rendering, so this is a renderer target, not a rebuild.
  • Templates and opt-ins managed at org level; STOP handling wired to the consent lifecycle we defined for the talent pool. Compliance is part of the channel, not an afterthought.
  • In the marketplace install wizard, WhatsApp is just a channel checkbox — install Mia, tick WhatsApp, she's on the org's number.
HAVE: channel_open (Plivo voice)HAVE: widget schemas, session stateHAVE: consent lifecycle designBUILD: BSP integration + renderer + template mgmt
Ship first: Mia's onboarding flow end-to-end on WhatsApp for one pilot org. Measure: completion rate vs web embed on the same template — the research says it should roughly double. If it does, every template gets the checkbox.
ONE-PAGER · 06

Generic Intelligence API — one paved road for every BetterPlace product

Every internal team is about to wire up their own LLM key. I'd rather they all call us.

Why I want this

skillBetter wants summaries. Verify wants document extraction. Payroll wants anomaly explanations. ESS wants a Q&A box. Left alone, each team ships its own OpenAI integration with its own key, no guardrails, no cost visibility, and five different answers to "is this compliant?". We already run the hard parts — multi-provider routing, guardrails, credits metering, telemetry, private-cloud inference. Exposing that as one internal API makes AI Labs the intelligence layer for the whole company, not just the agent studio. And every internal consumer makes our platform better priced and better tested for external customers.

How it works on our platform

  • One internal API, three verbs to start: complete (prompt in, structured output out), extract (document in, schema out — reusing the OCR/IDP stack), converse (a headless agent session for products that want chat without building it).
  • Every call carries a product key → per-product credits, rate limits, guardrails, and telemetry out of the box. Finance sees AI spend per product in one place. That alone justifies the build.
  • Model routing stays ours: self-hosted for sensitive payloads, commercial models where quality demands — callers say what they need (fast/cheap/best), not which model. We keep the freedom to swap providers without ten teams changing code.
  • Data residency inherits automatically — "your data never leaves BetterPlace infrastructure" becomes true for every product, not just AI Labs.
  • This is ghost_operators' /invoke + the model resolver with a product-facing front door and quotas. Kong already sits in front. The build is mostly contract, keys, and quota plumbing.
HAVE: multi-provider resolverHAVE: credits, guardrails, telemetryHAVE: Kong gatewayBUILD: product keys, quotas, 3-verb contract, docs
Ship first: extract for Verify (they're already asking) with per-product credit reporting. Measure: number of internal products on the API, spend visibility coverage, and how many bespoke LLM keys we retire. Success is boring: nobody at BetterPlace wires a raw LLM key again.
ONE-PAGER · 07

Chat — a Claude-style workspace inside the console

We run the most capable models in the region and give our own users no way to just talk to them. Fix that.

Why I want this

Agents are periodic — you onboard someone, you fill a req. Chat is daily. Every admin, HR lead, and ops person in the console should be able to hit New chat and work with the best model directly: draft the policy note, analyze the attendance dump, ask questions against their own knowledge base, and walk away with a finished file. This is what makes AI Labs a habit instead of a tool you visit.

And it's not ChatGPT-with-extra-steps. The whole point is what's already plugged in: the org's knowledge, the org's connectors, our artifact generation, our guardrails, our private cloud. ChatGPT knows nothing about your company; this chat starts there. It's also our best agent-creation funnel — a chat someone repeats every Monday IS an agent waiting to be configured, so the "turn this into an agent" button belongs right in the thread.

How it works on our platform

  • A Chat item in the console sidebar: new chat, history, search. Sessions and history ride the chat_history module we already run.
  • Defaults to the most capable model via the resolver — users never pick a model, they pick a job. Same engine the Generic Intelligence API (one-pager 06) exposes to products; Chat is the human door, the API is the product door.
  • Attach the org's world per chat: knowledge base collections, connected tools and MCP servers (Drive, Slack, Gmail from one-pager 02), uploaded files. Everything scoped to the tenant, nothing leaves our infrastructure.
  • Artifacts in the thread (one-pager 01): ask for the report, get the DOCX/XLSX with a download card — same renderer, same provenance.
  • Same governance as everything else, for free: guardrails on every response, credits metering per seat, thumbs up/down (one-pager 03), full audit trail. IT gets one answer to "who's using AI on what".
  • "Turn this into an agent" — one click hands the conversation pattern to the NL builder as a draft. Chat becomes the top of the agent-creation funnel.
HAVE: chat_history moduleHAVE: model resolver, guardrails, creditsHAVE: KB + MCP attachment railsHAVE: NL builderBUILD: chat surface + file upload + agent-handoff
Ship first: New chat + history + best model + KB attach + artifact download, in the console sidebar. Measure: weekly active chatters per org, % of chats that touch org knowledge or tools (if it stays near zero we built a generic chatbot, not ours), and chats converted to agents per month.
