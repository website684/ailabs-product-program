Agent Templates & the AI Employee Marketplace

Turn the studio into a store. A template is a certified, versioned AI employee — Mia, Jack, Cole — that any org installs by binding its own knowledge, tools, and brand into declared slots. Ten minutes to a working agent stops being a demo claim and becomes the product.

1Why templates, why now

Today every agent on the platform is built from a blank canvas. That has three costs:

  • Time-to-value gap. The deck promises a working agent in 10 minutes; a real Mia-class onboarding agent takes days of prompt, step, widget, and guardrail work by someone who understands the platform. The people we sell to — HR ops, staffing leads — are exactly the people the blank canvas excludes.
  • Repetition without leverage. Every Subway-like customer needs the same onboarding workflow with different documents, tools, and branding. We rebuild the fixed 80% per customer and charge for the privilege of waiting.
  • The roster is marketing, not product. Mia, Jack, Cole, Max, Ivy, Theo exist on the website as personas. Nothing in the product lets a customer "hire Mia". Templates make the roster literal: each persona is a certified template with an install button.
The positioning already tells us the mental model: "You don't buy software. You hire AI employees." A marketplace listing is a candidate profile. Installing is onboarding a new hire: give them workspace access (knowledge, tools), a manager (HITL approver), and a uniform (brand). The install wizard should read like an onboarding checklist — our own product philosophy applied to ourselves.

Multi-tenancy is the hard part and the moat. Each org has different knowledge bases, tool credentials, MCP endpoints, languages, and brand. A template system that survives contact with two customers has to draw a precise line between what the template owns and what the tenant owns. That line is this PRD's core design decision.

2Template anatomy: three layers

Every template package splits into fixed (versioned, certified, vendor-owned), bound (resolved per tenant at install), and tunable (safe prompt slots an org can edit without forking). Mapped to the real config model:

Config fieldLayerMechanism
chat_workflow_steps / workflow_stepsFixedImmutable per template version. Steps, widgets, completion criteria, bindings ship as-is — this is the certified behavior.
tool_ids / mcp_serversFixed capability, bound instanceTemplate declares required capability types ("HRMS write", "WhatsApp send", "OCR extract"). Install resolves each to the org's actual tool/MCP credential. No secrets ever ship in the artifact (n8n rule). Platform-provided tools (WhatsApp BSP, OCR, calendar) are always-available capabilities — pre-certified, zero setup.
document_idsBound, alwaysTemplate defines document slots (required doc types + resync cadence, e.g. "HR policy pack", "store SOPs"). Org attaches its own KB at install (Lindy pattern). Never in the artifact.
guardrail_policyFixed floor, org-tightenableTemplate ships a non-negotiable floor (e.g. Mia: pii_masking + consent events ON). Orgs may tighten, never loosen. Field-level manageability flags (Salesforce 2GP pattern) mark what upgrades may touch.
ui_config / voiceBound, alwaysBrand theme, avatar, launcher; voice ID and telephony number. Template only fixes whether voice is supported.
language[]Fixed certified set → bound subsetTemplate ships languages its prompts/voice were certified in; org activates a subset. New language = re-certification, not a config edit.
Prompt sub-slotsTunableMarked regions inside step prompts ("tone of greeting", "escalation phrasing") editable via natural language within the guardrail floor (Sierra Ghostwriter / Fountain Cue pattern). No fork, no new version.

3The install experience

Browse roster→ Preview (workflow map · sample chat · what you'll configure)→ Install wizard: bind 4 things→ Preflight→ Sandbox test on YOUR data→ Activate

The installer configures only the bound layer — four things, in order:

  1. Knowledge — attach documents to each declared slot (or pick existing KB collections). Ingestion/indexing starts immediately, in the background.
  2. Connections — resolve each required capability to an org tool/MCP. Platform-provided capabilities show as "Ready ✓" with zero work; org-specific ones (HRMS endpoint) open the existing tool form inline.
  3. Brand & channels — UiConfig theme, languages subset, channels (web, WhatsApp, voice). One install binds all channels (Microsoft 365 Agent Store pattern).
  4. People — HITL approver role, escalation inbox, credit budget cap.

Preflight blocks activation until: every capability resolves and authenticates; document slots ingested and indexed; guardrail floor intact; selected languages ⊆ certified set; theme renders; the template's scripted eval set passes in sandbox against the org's real bindings. Then a mandatory sandbox conversation — the admin talks to their Mia on their data before anyone else can. Activation flips the alias (§4); no publish without a passed preflight.

Time-to-value target: under 60 minutes from "Install" to activated agent when documents exist and only platform capabilities are needed; same-day when an org tool must be connected. Sierra's 4–10 week white-glove onboarding is the anti-pattern; Copilot Studio's guided one-click install is the benchmark. The wizard is the product demo — every minute in it must feel like progress, not configuration.

4Versioning & upgrades (the part that keeps working at customer #40)

  • Version/alias split. Template versions are immutable and numbered; each installed agent is an alias pointing at a version + its bindings. Upgrade = repoint the alias after preflight re-runs. Zero-downtime, instant rollback (AWS Bedrock alias / Agentforce pattern).
  • Draft → Commit → Activate lifecycle for template authors; only committed versions are installable, and commit is the certification checkpoint.
  • Per-field manageability flags decide what an upgrade may touch: vendor-managed (steps, floor) auto-propagates; org-bound (bindings, theme, tunable slots) is never overwritten.
  • Publisher-initiated, targeted push upgrades — choose which installs, which version, when; never silent push-to-all. Changelog + re-run preflight per tenant; failures hold the old alias.
  • Fork as escape hatch. An org needing structural changes forks into a plain custom agent — explicitly severing upgrade propagation, stated at fork time (Zapier model). Forking is a feature, not a failure: the template system feeds the custom studio.

5Marketplace shape

  • The roster is the storefront. Six personas as flagship first-party templates ("Official · by BetterPlace"), browsable by industry (QSR, retail, logistics, BFSI) and function (hire, onboard, verify, train, sell). Industry variants are distinct certified templates (Mia for QSR ≠ Mia for logistics), not one template reskinned — the Agentforce vertical-library pattern.
  • Quality signals that matter: live install count, outcome rate (resolution/completion), median time-to-activate — on the card. Star ratings alone are noise. The GPT Store's real failure was publish-then-invisible: 95%+ of listings undiscovered. Curated categories over infinite shelf.
  • Certification is staged (ServiceNow pattern): scope/architecture review of declared bindings → automated checks on every build (guardrail floor intact, no secrets in artifact, eval set passes) → manual review before listing (prompt injection, policy). Any change to fixed logic = new version + full re-cert. Automated-only review is how policy-violating GPTs stayed live — we don't repeat it.
  • Partner templates (phase 3): same certification gate + signed revenue-share; partner badge distinct from Official. Not before the first-party roster proves the rails.

6Commercials

Hybrid metering — every single-axis pricer in this market added a second axis within a year (Agentforce's flat $2/conversation, Sierra's pure per-outcome both bent):

  • Credits remain the substrate (existing billing) — consumption floor for every installed agent.
  • Per-outcome tier on top, defined in the template: the template marks its billable outcome step (billing.outcome_step_id — "candidate fully onboarded", "document verified"). Tiered by outcome value (Intercom Fin's $0.99 routine vs $9.99 high-value pattern), priced in ₹ per outcome on the listing. The card says what hiring this employee costs per unit of work — nothing else in the India/SEA market prices this way.
  • Enterprise: committed credit bundles + private templates (org-internal marketplace of their own certified agents).

8Metrics & phasing

  • North star: median install→activate time (target <60 min) and day-7 outcome count per install (an installed agent that does no work in a week is a failed install).
  • Guard metrics: preflight pass rate (low = binding UX broken), upgrade adoption rate, fork rate (high = fixed layer drawn wrong), sandbox-test completion before activate = 100% by construction.
PhaseScopeExit
P0 (3–4 wk)Template package schema + install engine, no UI: install "Mia — QSR onboarding" via API into 2 test orgs with different KB/toolsSame template, two working tenants, zero code between installs

9Risks & open questions

  • The fixed/bound line will be wrong somewhere. Mitigation: fork-rate as a tripwire per template; tunable slots absorb the most common "just this one prompt" pressure.
  • Upgrade trust. One bad push to installed tenants poisons the model. Mitigation: preflight-per-tenant before repoint, staged rollout, instant alias rollback.
  • Certification bottleneck at partner phase. Mitigation: don't open partner authoring until first-party cert pipeline is boringly repeatable.
  • Open: does an installed agent's template_ref lock the builder UI (view-only fixed layer) or hide it? Prototype assumes view-with-lock-badges.
  • Open: outcome-step billing needs finance sign-off on revenue recognition per outcome type.
  • Open: template-level analytics benchmarking across tenants (anonymized outcome rates as a listing signal) — privacy review needed.
